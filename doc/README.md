# LexJab Sim — декларація

Створено 18.11.2026 · Віталій · оновлено 18.11.2026

## Що це

Сайт-симулятор алгоритму повторення юнітів для LexJab.
Код лежить у **публічному** репозиторії на GitHub, сайт публікується на GitHub Pages.

Вимоги першої версії (режим дедлайну) — у [requirements.md](requirements.md).

## Навіщо

- **Видно все.** Код, правила й кожен прогін відкриті. Розрахунки йдуть у браузері, а не «десь у Python».
- **Будь-який пристрій.** Сайт відкривається з планшета й телефону. Кнопки Apps Script у Google Таблицях на планшеті не спрацьовують.
- **Масштаб.** Google Таблиці не тягнуть великих колод: аркуш SM-2 на 100 юнітах / 25 за урок перераховується дуже повільно.
- **Можна показати.** Сайт придатний для демонстрації потенційним спонсорам.

## Рішення (18.11.2026)

- **Репозиторій публічний.** Алгоритм здебільшого повторює відомі підходи, до них додано власні правила. Комерційної цінності він не має.
- **Сайт автономний, у хмарі.** Репозиторій `Airteg/lexjab-sim` — єдине джерело. Віталій дає інструкції Claude, а Claude вносить зміни через pull request; Віталій переглядає і зливає. Локальний ПК для роботи не потрібен.
- **Стек:** Vite + React + TypeScript, статичний сайт без сервера (див. requirements.md). Збірку й публікацію виконує GitHub Actions.
- **Модуль алгоритму відокремлений від сайту.** Це один модуль для симулятора, прототипу і майбутнього iOS. Модуль має версії.
- **Прототип не змінюємо, доки алгоритм не готовий.** Сайт працює з муляжами даних у JSON.
- **Схема БД — результат роботи, а не вихідна умова.** Алгоритм визначає, які дані потрібні. Поточна схема прототипу (schema 4) — заглушка для петлі навчання.

## Режими

| Колода | Режим | Мета | Гарантія запам'ятовування |
|---|---|---|---|
| 100–200 юнітів | дедлайн | підготовка до дати | не гарантуємо |
| 100–200 юнітів | активна колода, SM-2 з термінами | перевірка забування | так |
| ~2000 юнітів (глобальна база) | чистий SM-2 | довготривале запам'ятовування | так |
| ~500 юнітів | не визначено (можливо, книжка) | — | розмір лишається параметром, окремого режиму немає |

**Гарантія = вимірний критерій.** SM-2 сам нічого не гарантує, він лише планує повторення. Юніт «дозрів», коли його інтервал ≥ 21 дня і учень пригадує його після паузи. Колода засвоєна, коли дозріли всі її юніти.

## Чим закінчується робота над алгоритмом

| № | Результат | Що всередині |
|---|---|---|
| 1 | Специфікація алгоритму (ТЗ — норма) | Правила й формули. Константи з рекомендованими значеннями та межами. Визначення «мета досягнута». Правило появи нових юнітів. Коли мета недосяжна. Контрольні приклади |
| 2 | Еталонна реалізація | Модуль алгоритму з тестами, готовий для прототипу |
| 3 | Рекомендована схема БД | Поля юніта й колоди, які потрібні модулю. Перелік змін відносно schema 4 |
| 4 | Докази | Симуляції за профілями учнів і розмірами колод. Мінімальний і оптимальний терміни, межі недосяжності. Відтворення прогонів |
| 5 | Взаємодія з учнем | Що додаток питає в учня: розмір колоди, юніти за урок, уроки на день, дедлайн. Що повідомляє: оцінку терміну, «мета недосяжна» |
| 6 | Межі | Що свідомо не охоплено |

## Структура

```
lexjab-sim/
├─ doc/
├─ packages/
│  ├─ core/   ← модуль алгоритму: черга під дедлайн, згодом SM-2
│  └─ sim/    ← модель учня, прогони, статистика
└─ apps/
   └─ web/    ← сторінка (GitHub Pages)
```

- Залежності йдуть в один бік: `web → sim → core`.
- Що модуль робить і чого не робить, описано в requirements.md.
- Генератор оцінок, модель забування й статистика живуть у `sim`.

## Етапи

### Етап 1. Режим дедлайну

Переносимо модель експерименту 2 (17.11.2026) без змін. Правила, функції й вимоги до модуля — у requirements.md.

**Критерій готовності:** сайт відтворює результати експерименту 2, які порахувала Python-програма. Якщо збігаються, сайт стає єдиним джерелом розрахунків.

### Етап 2. SM-2 з термінами

- **Модель забування в `sim`.** Імовірність пригадати падає з часом після повторення. Модель беремо з джерел (наприклад, FSRS), не вигадуємо. Без неї інтервали SM-2 нічого не перевіряють, бо оцінка однакова через день і через місяць.
- **Одиниця часу — день.** Обмеження: ліміт дій на день (25–80) і правило появи нових юнітів.
- **Зниження EF після провалу — експериментальна константа.** В експерименті 1 зі зниженням колода на 100 юнітів тривала 276 днів (13 юнітів застрягли на EF 1,3), без зниження — 137 днів.
- **Інтервал.** У таблиці `progress` прототипу його немає, а SM-2 рахує новий інтервал із попереднього. Це піде в рекомендацію до схеми.

## Додаткові вимоги до сайту

Доповнюють розділ «Функції» в requirements.md.

- **Збереження результатів:** журнал прогону й підсумки можна зберегти в JSON / CSV і відкрити знову на сайті чи в Google Таблицях — «порахувати один раз, дивитися під різними кутами».
- **Журнал прогону** — у форматі, близькому до `review_log` прототипу, плюс номер уроку й версія алгоритму.
- **Прозорість:** сторінка показує, які правила й константи діяли в прогоні.
- **Продуктивність:** розрахунки йдуть у Web Worker, щоб сторінка не зависала на великих колодах.
- **Тести:** правила модуля й контрольні приклади перевіряються на GitHub при кожному коміті.

## Поза межами (поки що)

- Ознайомлення з новими юнітами в режимі дедлайну.
- Перенесення юнітів із колоди з дедлайном у глобальну базу: з якими оцінками.
- Режим для колод ~500 юнітів.
- Інтеграція з прототипом.

## Відкриті питання

- Відповідність кнопок оцінкам прототипу: «Ще раз» = `AGAIN`, «Повторити» = `GOOD`, «Добре» = `EASY` — не затверджено.
- Модель забування для етапу 2.
